POLYGRAPH -- DEMO / PITCH SCRIPT
===================================
Target: ~2.5-3 minutes spoken, built around the two live demo
scenarios already committed in examples/fixtures/. Timing marks are
approximate (~150 wpm) -- read it once out loud and adjust to your
own pace before the real thing.

Setup, before you're called up: have a terminal open, already `cd`ed
into the polygraph repo with the venv activated, font size big enough
to read from the back of the room, and both commands below typed out
(not yet run) so there's no fumbling.

--------------------------------------------------------------------------------
[0:00-0:15] HOOK
--------------------------------------------------------------------------------
SAY:
"A 2026 paper called ShadowPickle built an attack to beat AI model
safety scanners -- it got past them sixty-three percent of the time.
Every major hosting site, Hugging Face included, still uses scanners
built exactly that way."

--------------------------------------------------------------------------------
[0:15-0:45] THE GAP
--------------------------------------------------------------------------------
SAY:
"Those scanners -- picklescan, fickling, ModelScan, Hugging Face's own
-- are all static. They read bytecode and guess, never actually load
the file, so none can tell you what it actually does.

The other half already exists too, just not for AI models: a project
called OSSF Package Analysis actually sandboxes a file and watches it
run -- for regular packages. It has the sandbox. It has no idea what
the package claims about itself.

Nobody's put those two things together for AI models. That's
Polygraph."

--------------------------------------------------------------------------------
[0:45-2:00] LIVE DEMO -- run both commands for real, don't fake it
--------------------------------------------------------------------------------
SAY, before running scenario 1:
"Here's a model checkpoint. It CLAIMS to be safetensors format --
that's the safe, modern format that can't execute code, period. Let's
check it."

RUN:
    polygraph examples/fixtures/malicious_pickle.pkl \
        examples/fixtures/claim_mismatch.json

SAY, pointing at the red table:
"Both checks go red. It's lying about its own format -- it's actually
an old-style pickle file, which CAN execute code. And when we actually
loaded it in an isolated sandbox, it tried to run a command. Caught.
That's the obvious case -- a static scanner would've caught the lie
too, just from reading the bytes."

SAY, before running scenario 2 -- THIS IS THE MOMENT THE PITCH HANGS ON:
"But watch what happens when the file is HONEST about what it is."

RUN:
    polygraph examples/fixtures/malicious_pickle.pkl \
        examples/fixtures/claim_pickle.json

SAY, pointing at the mixed table:
"Same malicious file. This time it truthfully says 'I'm a pickle
file.' Format check: green. No lie. Every static scanner on the
market stops right here and calls this fine, because there's nothing
dishonest to catch.

But we didn't just check the label. We actually ran it, in an
isolated sandbox with no network and a read-only filesystem. Red.
It tried to run a command the second we loaded it. An honest label
is not the same thing as a safe file. That's the whole pitch."

--------------------------------------------------------------------------------
[2:00-2:30] WHY IT'S HARD (the judge who cares about engineering, not just the demo)
--------------------------------------------------------------------------------
SAY:
"This is real process isolation, not a wrapper -- bubblewrap, the
same sandboxing tech behind Flatpak, with the filesystem read-only
except one scratch folder and the network fully disconnected, not
just firewalled.

We even found a real gap in our own first version: an attack outside
the sandbox got blocked, but left no trace we were checking for, so
it silently reported safe. We caught it by deliberately trying to
break our own tool -- same falsification-first process behind our
other two projects."

--------------------------------------------------------------------------------
[2:30-2:45] CLOSE
--------------------------------------------------------------------------------
SAY:
"Polygraph doesn't ask a model what it claims to be. It watches what
it actually does. A lie detector for AI models."

(stop talking here -- let the last line land, don't undercut it with
more words)

--------------------------------------------------------------------------------
IF THERE'S TIME FOR Q&A -- LIKELY QUESTIONS
--------------------------------------------------------------------------------
Q: "Does this replace picklescan/those other scanners?"
A: "No, they're fast and complementary -- ours actually runs the
   file. Best case is both: static first, behavioral as the deeper
   check."

Q: "What happens with a real, huge model file, not your tiny test
   fixture?"
A: "Same mechanism, it just hasn't been run at that scale yet --
   that's a named gap, not something we've solved. To be precise:
   Polygraph doesn't do syscall tracing. It watches side effects --
   does anything get written outside the one scratch directory it's
   allowed to touch, does the process hit something the sandbox
   blocks and leave a signature in stderr. That check doesn't get
   more complex with file size. What could actually break at scale is
   different: does loading a multi-gigabyte checkpoint blow past the
   sandbox's timeout, and for safetensors specifically, does it stay
   cheap -- since that format only ever reads the header, not the
   tensor data itself. Those are the real open questions, and they're
   untested."

Q: "Isn't a sandboxed process still risky to run at all?"
A: "Yes, and we don't claim otherwise -- no userspace sandbox is a
   perfect boundary. bubblewrap gives strong isolation, not absolute
   isolation: no network access at all, one writable scratch
   directory, everything else locked down. It's the same sandboxing
   primitive Flatpak uses to isolate every desktop app on Linux, so
   it's a proven, widely-deployed tool, not something we built from
   scratch. The honest caveat: a sophisticated enough kernel-level
   exploit could theoretically escape any userspace sandbox, including
   this one. We actually found and fixed a real isolation gap
   ourselves during development, which is the kind of testing this
   needs -- not a build-once-and-hope. If someone needed a harder
   boundary than this, the upgrade path is something like gVisor or a
   full VM -- the same approach OSSF Package Analysis actually uses --
   which is a reasonable next step, not a redesign."
