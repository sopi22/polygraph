4. PHASE 0 -- SEARCH, DECIDE, AND ACT
================================================================================

RESEARCH QUESTION (this project's own, feeding the search below):
Does a self-declared safety claim about an AI model checkpoint (e.g.
"safetensors only, no pickle", "no custom code executed on load")
actually match what the artifact does when loaded inside a sandbox
that can observe real behavior -- and does combining that claims-check
with a real sandboxed load surface risk that neither check alone
would catch?

STEP 1 -- SEARCH (actually fetched and read each project's own
  docs/README, not a one-line description, before logging anything
  here):

1. picklescan (mmaitre314/picklescan) -- static only. Disassembles
   pickle opcodes via stdlib `pickletools`, flags dangerous
   GLOBAL/REDUCE calls against an allow/block-list. Never loads or
   executes the file. Has a documented bypass (GHSA-jgw4-cr84-mqxg).
   License: MIT. 418 stars, 3 open issues, last pushed 2026-07-23 --
   active, small, healthy.

2. fickling (trailofbits/fickling) -- static/symbolic only. Decompiles
   pickle bytecode to readable Python and symbolically executes the
   VM's stack operations -- explicitly designed to be safe to run
   because it never really executes the payload.
   License: LGPL-3.0. 662 stars, 13 open issues, last pushed
   2026-08-13 (yesterday) -- actively maintained, backed by a
   professional security-research firm.

3. ModelScan (protectai/modelscan) -- static byte-pattern scan across
   pickle/H5/SavedModel/Keras-V3. Never loads the model.
   License: Apache-2.0. 762 stars, 77 open issues, last pushed
   2026-02-18 -- roughly six months stale relative to today; still
   the most-starred of the three, but showing less recent activity.

4. Hugging Face Hub's own scanning (Pickle Import Scan + ClamAV +
   Protect AI Guardian) -- three layered, all-static checks built
   into the Hub itself, not a standalone repo to fork. HF's own docs
   explicitly disclaim completeness ("not 100% foolproof").

5. OSSF Package Analysis (ossf/package-analysis) -- the closest
   architectural precedent to what this project wants for its
   sandbox layer: a real gVisor sandbox with strace + packet capture,
   for npm/PyPI packages, logging file/network/subprocess behavior
   and diffing it release-over-release.
   License: Apache-2.0. 903 stars, 83 open issues, last pushed
   2026-08-07 -- actively maintained, OpenSSF-governed (strong
   institutional backing, low bus-factor risk at the project level).
   Scoped to generic npm/PyPI packages, not ML checkpoints, and built
   as continuously-running infrastructure (Go, GCP, BigQuery, Cloud
   Run) for scanning the entire package firehose at scale -- not a
   single-machine, bounded research tool.

None of the five do the specific thing this project asks: cross-check
a checkpoint's OWN declared safety claim against what a sandbox
actually observes when it's loaded. The static tools (1-4) never
execute anything, so they have no behavioral signal to check a claim
against. OSSF Package Analysis (5) has the behavioral signal but no
claims layer at all, and isn't scoped to ML checkpoints.

Corroborating evidence this gap is real, not just unnoticed: an
academic attack purpose-built to evade static pickle scanners
(ShadowPickle, arXiv 2607.17503) reports a 63% bypass rate against the
current generation of tools like (1)-(4) -- a published number, not a
guess, that static-only scanning has a real, demonstrated hole a
behavioral layer would help close.

STEP 2 -- DECIDE (fork vs. inspiration-only vs. independent, tradeoffs
  stated explicitly, per this template's own requirement):

REUSE EVALUATION, against the template's named criteria:
  Maturity: all four real repos (1,2,3,5) are mature, real projects
    with hundreds of stars and years of use -- not the concern.
  Maintenance activity: picklescan, fickling, and OSSF Package
    Analysis all show pushes within the last week; ModelScan is the
    one showing real staleness (~6 months) among the four.
  Documentation quality: all four have real, readable docs (fetched
    and read directly, not assumed from a landing page).
  Security history: fickling and picklescan both exist specifically
    because of documented real-world pickle exploitation history in
    this exact space -- a point in favor of their domain judgment,
    not a red flag.
  License compatibility: MIT (picklescan), LGPL-3.0 (fickling),
    Apache-2.0 (ModelScan, OSSF Package Analysis) -- all permissive
    enough to fork under, if forking were the right call. Not the
    blocker either way.
  Community adoption: real (400-900+ stars each) but, per this
    template's own instruction, never treated as the deciding factor
    on its own.
  Bus factor: picklescan is the smallest team by a wide margin (a
    personal/small-maintainer project judging by issue-response
    pattern); fickling and ModelScan are corporately backed (Trail of
    Bits, Protect AI); OSSF Package Analysis is foundation-governed --
    lowest bus-factor risk of the four, structurally.
  Red flags: none found for any of the four -- no abandonment,
    ownership churn, or license-change history surfaced in this pass.

WHY NOT FORK ANY OF THEM: the architectural mismatch is the real
  reason, not any of the criteria above. picklescan/fickling/ModelScan
  are built around NOT executing the payload -- their entire design
  philosophy is the opposite of what this project needs (a real
  sandboxed execution). Adding real sandboxing to any of them would
  mean replacing their core mechanism, not extending it -- there is no
  meaningful fork-and-add-a-feature path here, only fork-and-rewrite,
  which isn't really forking. OSSF Package Analysis has the right
  mechanism (real sandbox, real behavioral logging) but is built as
  continuously-running cloud infrastructure (Go, GCP, BigQuery, Cloud
  Run) for scanning an entire package ecosystem at internet scale --
  forking it would import that whole infrastructure surface for a
  single-machine, bounded, falsification-first student research
  project that needs none of it. The mismatch is in scale and
  operating model, not code quality.

DECISION: build independently (Section 7), not fork (Section 5/6 do
  not apply -- no license-check gate triggered, no repo-visibility
  hold needed on that basis). picklescan, fickling, ModelScan, and
  OSSF Package Analysis are all named in the README as design
  influences/prior art, per this template's Section 7 instruction --

14. NEW PROJECT
================================================================================
What it is and why: Polygraph checks whether an AI model checkpoint's
  own declared safety claim (e.g. a model card saying "safetensors
  only, no pickle, no custom code on load") matches what actually
  happens when the checkpoint is loaded inside an isolated sandbox --
  a claims-vs-behavior cross-check that, per Section 4's search, does
  not currently exist as a shipped tool for ML checkpoints, and only
  half-exists (behavioral half only, no claims half) for generic
  software packages.

Priority-ordered v1 features (Phase 1, not yet built):
  1. `sandboxed_load` check -- bwrap-isolated load of a checkpoint
     file (network fully unshared, filesystem read-only except one
     scratch dir), observing PASS/FAIL on whether anything happened
     outside the declared boundary.
  2. Deliberate FAIL-detection case for check 1 (required before any
     PASS result counts, same discipline Pulse and Claim Card both
     hold themselves to): a hand-constructed malicious pickle payload
     (the well-documented `__reduce__` -> `os.system` technique)
     confirmed to actually get caught as FAIL, not silently pass.
  3. `declared_format_cross_check` -- compares a checkpoint's claimed
     format (from an accompanying model card/doc) against its actual
     raw-byte format (pickle vs. safetensors), independent of check 1.
  4. A combined report (single JSON file, one predictable location,
     Section 12) showing both checks' results together per artifact --
     the actual new synthesis this project is testing, not either
     check alone.

Full research hypothesis, falsification criteria, vocabulary lock, and
  entropy budget are in RESEARCH_HYPOTHESIS.txt (kept as a separate
  file this time, rather than folded into this template's own Section
  4, so this brief stays a clean match to the operator-supplied
  template structure and the falsification framing stays a clean
  match to her other two projects' own convention).

Course/context overrides to Sections 8-12: none -- all apply as
  written above.
