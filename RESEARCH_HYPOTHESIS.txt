POLYGRAPH -- RESEARCH HYPOTHESIS, VOCABULARY LOCK, ENTROPY BUDGET,
AND CHECK SELECTION
=====================================================================
Companion to RESEARCH.txt (the operator-supplied "Fork or Build"
template brief, Sections 0-14). This file holds the falsification-
first framing in the same convention Jhoana's other two projects
(FOSS Pulse, Claim Card) already use, so it isn't folded awkwardly
into a template section that wasn't built for it. See RESEARCH.txt
Section 4 for the full novelty-firewall search this hypothesis is
downstream of -- not repeated here.

================================================================================
1. RESEARCH HYPOTHESIS FRAMING
================================================================================

RESEARCH HYPOTHESIS (H1):
A checkpoint's self-declared safety posture can be checked against
what it actually does when loaded inside an isolated sandbox, and the
two signals together (declared claim + observed behavior) surface
risk that neither the claim alone nor a single sandboxed run alone
reliably would.

NULL HYPOTHESIS (H0):
The sandboxed behavioral signal always simply agrees with what a
cheap static structural check (is the file pickle-format or
safetensors-format?) already implies -- the sandbox adds no
information a static check didn't already have.

FALSIFICATION CRITERIA (stated in advance):
- Toward H1: any case where the declared claim and the sandboxed
  observation disagree -- especially one a static structural check
  alone would have missed.
- Toward H0: across all test artifacts, the sandboxed observation
  always agrees 1:1 with the file's structural format alone -- a
  complete, honest, non-failed result, not something to keep
  re-running until it looks better.
- SEPARATE, PRIOR gate before either of the above can mean anything:
  the sandbox's own deliberate FAIL-detection case (Section 3 below)
  must actually catch a synthetic malicious payload. If it doesn't,
  that's a probe-implementation defect, not evidence about H1/H0
  either way -- the same FAIL-detection discipline both her other
  projects require before trusting any PASS result.

WHAT WOULD CHANGE MY MIND:
A clean, reproducible divergence between claim and behavior is the
interesting result (supports H1). Total agreement across every real
artifact tested is also a complete, honest experiment (supports H0),
not a failure to explain away.

================================================================================
2. VOCABULARY LOCK AND ENTROPY BUDGET
================================================================================

Locked: claim, probe, observation, sandbox, cross-check. (Deliberately
  reusing Pulse's "probe/observation" and Claim Card's "claim" -- this
  project is an explicit synthesis of both, not a fresh vocabulary.)
Forbidden: verified, proven, guaranteed, confirmed, safe, malicious --
  about what this tool's own output claims. A sandboxed observation is
  a flag for human review, not a finding of fact -- same epistemic
  posture Claim Card already enforces on its own output.

Entropy budget:
  Check types: 2 maximum for Phase 1 (sandboxed behavioral load,
    declared-format structural cross-check) -- deliberately not using
    the full headroom either sibling project left itself.
  Persistent format: 1 (JSON), matching both sibling projects.
  Sandbox mechanism: 1 (bubblewrap) -- see RESEARCH.txt Clarification
    Gate for why, and why Docker is named but deliberately not used.
  Network calls from the framework itself: 0. Test artifacts are
    constructed locally, not fetched live per run.
  External services: 0.
  Background processes: 0.
  Dependencies: stdlib only at runtime (pickletools, struct, json,
    subprocess to invoke bwrap). No torch, no safetensors package.
    pytest as a dev-only dependency, same justification pattern as
    both sibling projects.

================================================================================
3. CHECK SELECTION AND JUSTIFICATION
================================================================================

CHECK 1 -- sandboxed_load (behavioral, Pulse's DNA)
  Assumption under test: loading this checkpoint file touches nothing
  outside one declared scratch directory and makes no network attempt.
  Mechanism: `bwrap` with the real filesystem entirely read-only
  except (a) the checkpoint file itself, read-only, and (b) exactly
  one throwaway scratch directory, read-write; `--unshare-net` with no
  interface configured, so any socket call needing the network fails
  at the kernel level rather than silently succeeding.
  Observation: PASS if the load completes and nothing appeared outside
  the scratch directory. FAIL if a write outside it, or a network
  attempt, is observed.
  DELIBERATE FAIL-DETECTION CASE (required before any PASS result
  counts): a synthetic malicious pickle payload using the
  well-documented `__reduce__` technique (a class whose `__reduce__`
  returns `(os.system, ('touch <path-outside-scratch-dir>',))`),
  confirmed to be observed as FAIL, not PASS -- proving the probe can
  actually detect exploitation, not just always report PASS by
  construction. Directly mirrors Pulse's own storage_write-against-
  /system pattern.
  Named limitation (stated in advance): bwrap isolates what's visible
  to the sandboxed process, but a payload that only touches what IS
  visible to it (the checkpoint file, the scratch dir) can't be
  distinguished from legitimate behavior by this check alone -- the
  same category of limitation Pulse names for adb's shell UID not
  matching an installed app's own sandboxed UID.

CHECK 2 -- declared_format_cross_check (structural claims, Claim
  Card's DNA)
  Assumption under test: a checkpoint's accompanying claim about its
  own format matches what the file's own bytes actually are.
  Mechanism: read the claim from a companion doc (reusing Claim
  Card's own doc-discovery convention where it fits) and independently
  determine the file's real format from its raw bytes -- a valid
  safetensors file starts with an 8-byte little-endian header length
  followed by a parseable JSON header (stdlib `struct`+`json`, no
  library needed); a pickle file's opening bytes disassemble as
  pickle protocol opcodes (stdlib `pickletools`).
  Observation: PASS if the claim and the actual format agree. FAIL if
  they disagree in either direction.

THE CROSS-CHECK (the actual new synthesis, not either check alone):
  report both checks' results together for the same artifact. Cases
  named in advance:
    - format claims safe, sandboxed load also clean: expected,
      boring, still logged (agreement is data, not noise).
    - format claims safe but structurally IS pickle (or vice versa):
      CHECK 2 alone already catches this -- named so it's clear this
      case does NOT require the sandbox to find, and isn't claimed as
      evidence for H1 on its own.
    - format is genuinely safetensors (structurally confirmed, so no
      code-execution surface exists in the format itself) AND the
      sandboxed load is clean: the strongest "no interesting
      information" case -- both signals agreeing for a structural
      reason, not by luck.
    - the case H1 actually needs at least one of, to be properly
      SUPPORTED rather than just plausible: a case where the two
      signals would have disagreed and only having both caught it.
      Not yet known to exist -- Phase 1's job to look for it, not
      assumed here.

4. FALSIFICATION REPORT (R0 -- Phase 1, bounded synthetic test set)
================================================================================

TEST SET: four hand-constructed fixtures (safe_safetensors.bin,
  safe_pickle.pkl, malicious_pickle.pkl,
  malicious_pickle_outside_scratch.pkl) plus three claim files, all
  built with stdlib only (examples/fixtures/build_fixtures.py). No
  real downloaded Hugging Face checkpoint used yet -- named in Section
  1's Clarification Gate as a later rung, not required to start.

CHECK 1's OWN FALSIFICATION GATE (must pass before any PASS result, or
  either H1/H0 reading below, counts):
  BUG FOUND AND FIXED DURING THIS WORK, before declaring the check
  done -- caught by deliberately testing the harder case, not assumed
  safe from the easier one: the first implementation's FAIL logic
  checked only (a) whether anything appeared in the scratch directory
  and (b) the sandboxed process's exit code. A payload targeting an
  absolute path OUTSIDE scratch, with its own stderr redirect also
  targeting a path outside scratch, is silently blocked by the
  sandbox (confirmed: the marker file never appears anywhere) but
  `os.system()`'s own failure never raises in the parent process, so
  the process still exits 0 and scratch stays empty -- both FAIL
  conditions miss it entirely, and the check reported PASS for a
  confirmed-blocked escape attempt. Root cause: the shell's own
  "cannot create <path>: Read-only file system" message leaks into the
  captured stderr even though nothing was written and nothing raised.
  Fixed by also checking stderr for host-kernel escape-attempt
  signatures (checks/sandboxed_load.py's
  _ESCAPE_ATTEMPT_SIGNATURES). Both deliberate FAIL cases -- the
  original (marker file written into the scratch-dir/CWD) and this
  harder one (absolute path outside scratch) -- are now caught
  correctly, re-verified after the fix, and both fixtures are
  committed permanently to the test set (tests/test_sandboxed_load.py)
  so this can't silently regress.

CHECK 2's OWN FALSIFICATION GATE: the deliberate mismatch case
  (malicious_pickle.pkl paired with a claim of "safetensors") is
  correctly caught as FAIL. Both honest-claim cases correctly PASS.

RESULT ON H1 vs. H0:
  Within CHECK 2's own narrow question (does the declared format claim
  match the actual format?), nothing new was found in this bounded
  set -- every fixture's claim was either deliberately honest or
  deliberately dishonest, and CHECK 2 caught the dishonesty correctly.
  A check correctly doing the thing it was built to do is expected
  behavior, not itself evidence toward H1.

  The genuinely new information this run surfaced: malicious_pickle.pkl,
  paired with an HONEST claim of "pickle format" (CHECK 2: PASS -- no
  format dishonesty at all), still produced a confirmed-dangerous
  sandboxed-load result (CHECK 1: FAIL). A reviewer relying on CHECK 2
  alone -- or on any static tool that only validates whether a format
  claim is honest, which describes every static scanner named in
  RESEARCH.txt's novelty firewall -- would see nothing wrong with this
  file: it truthfully says it's a pickle file, and it is one. Only
  CHECK 1's behavioral signal caught the actual risk. This is
  precisely the case Section 3's "THE CROSS-CHECK" named in advance as
  the one H1 actually needs: the two signals' practical implications
  diverge (one says "no labeling problem," the other says "dangerous
  behavior"), and only having both caught the real issue.

CAVEAT, stated plainly, not glossed over: this is a synthetic,
  deliberately-constructed case -- I built the malicious fixture
  myself, already knowing it was malicious. It demonstrates the
  MECHANISM works as designed (the combination CAN surface exactly
  this class of case), not that this class of case occurs naturally in
  real, independently-authored checkpoints. That is a materially
  different, weaker claim, and the distinction is named here on
  purpose -- the same distinction Claim Card's own Section 10 drew
  between "checks work on a synthetic fixture with known ground
  truth" and "checks find something on a real repo with
  naturally-occurring content."

CONCLUSION: SUPPORTED for the mechanism, on a single bounded synthetic
  test set (R0) -- the combination of a claims check and a behavioral
  sandbox genuinely catches a class of case neither check surfaces
  alone, demonstrated directly rather than merely argued for. NOT yet
  evidence that this class of case occurs in real, naturally-authored
  checkpoints -- no real artifact has been tested. One observation, one
  bounded pilot -- not generalized further, same restraint Autopsy
  Experiment #001 already applied to itself in this project family.

RECOMMENDED NEXT EXPERIMENT (open item, not scheduled): test against a
  real downloaded Hugging Face checkpoint -- a genuine safetensors file
  and a genuine legacy-format pickle/.bin file from an actual public
  repo -- to see whether both checks produce the same clean signal on
  real-world artifacts as on the hand-built ones here. This is the
  natural R1 rung, mirroring Pulse's own R0 (synthetic/local) -> R1
  (first real device) progression.
